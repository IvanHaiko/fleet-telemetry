# Inspecting unfamiliar PX4 recordings and diagnosing stale telemetry

Design proposal for the local recording profile, 2026-11-17. The smallest useful change is an offline answer to “what can I see in this file?” The highest monitoring priority is a separate question that already applies to supported runs: “why has this value stopped updating?”

## Starting point and open MVP results

ADR-0057 is proposed and implemented for F09, F07 and F03. Its integrated analytical path rejects an unregistered file before parsing. It records successful complete runs and archive-only rebuilds for F07 and F03 as well as the F09 compatibility comparison. Opening an unknown file for structural inspection requires a second entry point. Admitting its measurements into the existing pipeline would change the ADR-0057 rule and requires a separate decision. [ADR-0057](adr/0057-registered-recordings-in-the-integrated-path.md)

MVP acceptance remains with the maintainer. F09 passed seven of eight declared conditions. Profile volumes grew 639.7 MB against a 512 MiB disk budget. The ClickHouse logging fix was checked on ClickHouse alone. The live final passed six of eight conditions, failing mid-run health and resource sampling. The fixes were checked in a short live debug session. Neither full final was repeated. The F09 capture-to-browser figure of about 11.1 s is a calculation from SQL visibility, sampling, refresh and query time. A direct measurement would trace one identified observation from capture through its first visible browser render. These results remain open when deciding whether to close the MVP evidence gaps or start the offline increment. [Final runs and timing calculation](adr/0056-run-health-without-a-monitoring-stack.md) · [Roadmap](roadmap.md)

## 1. Give the operator an offline inventory

ULog contains field definitions, subscriptions and data frames. Read the definitions from the actual file, associate each subscription with its topic and instance, and count its frames. Start with a local command that returns one row per subscription and a short summary of available views. This gives the operator an answer without starting Kafka, Flink, ClickHouse or Grafana. [ULog specification](https://docs.px4.io/main/en/dev_log/ulog_file_format) · [Existing integrity scanner](../ulog_integrity.py)

Give the inventory its own structural admission policy. Reuse bounded frame and layout decoding. The existing scanner also has checksum-specific service-frame allowances and resource limits, so calling it with an unfamiliar digest does not by itself implement generic inspection. Publish the supported format versions, features and input limits. Return an explicit incomplete or unsupported result on detectable corruption, an unsupported feature or an exceeded bound. Report dropout markers separately from observed sample counts.

For each subscription show the field names and types, instance, sample count and mapping status. A schema match on an unfamiliar file can be reported as a candidate. Display interpreted values only where an existing reviewed inspection path admits them. Summarize absent subscriptions for the capabilities the operator asked about. Preserve the difference between a missing subscription, an empty one, an unknown mapping and a stream with samples rejected by a reviewed mapping.

**Acceptance example.** On F01 the report explains the empty map (GPS subscribed, zero samples), the empty battery panel (no subscription), and the available recorded state (41 land-detector and 77 commander samples). The existing F01 inspection supplies the state timeline. On an unregistered fixture with a custom topic and two instances, the same command lists the two counts and their fields with no registry edit. This second case demonstrates discovery independently of F01's special admission rules. [F01 inspection evidence](guides/two-recording-view.md)

## 2. Admit compatible recordings to the existing analytical path

**Proposed change to ADR-0057.** When a second flight needs the same reviewed analytics, introduce a successor admission rule for the existing producer and consumers. Match the selected topics' definition hashes (including referenced layouts) **and** an explicitly reviewed firmware revision or evidenced range for that mapping. An unknown revision, missing required topic or unsupported definition yields an explicit reason for the unavailable capability. A file can still be inspected offline. Broader firmware ranges require evidence for units, sentinels, enums and clocks throughout the range. F03 and F07 assign different meanings to navigation code 8. F03 also records integer GPS coordinates in units of 10⁻⁷ degrees and lacks a sample timestamp. [Reviewed firmware differences](adr/0057-registered-recordings-in-the-integrated-path.md)

Keep the SHA-256 of each original for provenance and identity. Measure record counts per file and reconcile them through preparation and serving. Keep source rights, vehicle attribution, clock evidence, integrity checks and resource bounds explicit for each input. A reviewed firmware mapping supplies no evidence of physical vehicle identity. Introduce a versioned mapping profile for new files because existing profile names and validators incorporate each registered recording's key. Keep the legacy recipes for registered runs. This step uses the existing analytical stream and has no dependency on a raw Kafka consumer. [Current profile and identity contracts](data-contracts.md) · [Current preparation checks](../runtime/flight_analytics/stream_source.py)

**Acceptance example.** Two different originals on the same reviewed firmware and layouts pass the same mapping without a per-file registry entry and retain distinct source identities. Changing just the firmware to an unreviewed revision with identical layouts leaves the data inspectable and the mapping unavailable. Reprocessing F09 must reproduce its stored reference IDs and content.

## 3. Decide on raw streaming when a consumer needs it

A concrete use case would be a downstream subscriber that needs high-rate custom messages as they are replayed. Once such a consumer is identified, write a separate ADR covering the following decisions and measurements before implementing a raw producer.

| Decision | Evidence required |
| --- | --- |
| Wire encoding | The current analytical bundle uses JSONL. Generic JSON numbers can lose large integers in binary64 consumers, and standard JSON numbers cannot represent NaN or ±Inf. Compare original ULog payload bytes plus a versioned envelope with an explicitly typed encoding. Specify array shape, signedness, nonfinite values and dependency cost. Round-trip a maximum uint64, an array, NaN and both infinities in the intended consumer. |
| Schema ownership and lifetime | A low-cost candidate is a checksummed manifest stored by the archive writer with the retained original. It would carry all transitive definitions and their format version. Specify publication order, access, retention and how a consumer resolves a schema during live replay and archive-only recovery. Demonstrate both reads before choosing a separate schema service. |
| Volume and backpressure | Current preparation caps a bundle at 50,000 events and 64 MiB. Use the offline inventory and original frame sizes to measure peaks by topic and instance, estimate encoded and retained bytes, and compare with actual local limits. The ADR needs a bounded workload, a credible 1× throughput and disk budget, and a pause/resume or refusal policy. A small correctness fixture cannot establish capacity. [Preparation limits](../runtime/flight_analytics/stream_contract.py) |
| Order, clocks and identity | Use a source locator comprising the exact file digest, topic, instance and zero-based ordinal **within that subscription**, allocated before filtering. Retain file byte offset separately for interleaving and deterministic tie-breaking. A byte-changing trim or re-export starts a new identity space even for overlapping observations of the same flight. A repeat of the same bytes preserves locators. Specify how replay is paced across pauses and clock resets. |

The proposed raw ID identifies a source record. A mapped measurement is deterministically derived from the located record and its versioned mapping using the applicable measurement-ID recipe. A derived fact can cite several input measurements. A future raw consumer must recover the same registered measurement IDs and content as direct preparation for the same inputs. Both routes should be compared on the same fixture before enabling either route to publish into a common analytical run. [Measurement identity and provenance](data-contracts.md)

## Monitoring priority: explain why a value stopped updating

Present source mode, last observed source progress, archive progress and last query-visible progress together. Use the clocks already qualified in ADR-0054. Live battery and state can have receipt age only. A historical recording can report its playback position and age on its native timeline. Source silence alone cannot establish a failed sensor. [Live clock and gateway evidence](adr/0054-live-sitl-recording-profile.md)

| Operator sees | Evidence for the explanation |
| --- | --- |
| No recent live observations | A healthy gateway with aging receipts supports “source silent”. Missing gateway health yields “unknown”. If other streams advance, identify the silent stream and its instance. |
| Paused replay or end of recording | Show explicit publisher state and last acknowledged source position. EOF plus reconciled counts marks completion. A recorded dropout marker identifies a gap in the original. |
| Serving behind | Input and archive advance while query-visible progress stays fixed. Show the last visible observation and its age. If SQL advances but browser render time is unavailable, label browser delay unknown. |

A follow-up for storage monitoring is the remaining intervention time before archive lag meets a retention or disk limit. Base it on effective retention, the oldest unarchived record, byte growth and measured catch-up rate. Show unknown when the limiting inputs cannot be measured. [Retention incident](case-studies/kafka-retention-incident.md) · [Recovery gate](guides/production-recovery-gate.md)

### Unattended alerts and an independent F09 drill

ADR-0056 deliberately computes health on demand. Checking between invocations, persisting incidents and delivering notifications would introduce a continuously running responsibility. Keep on-demand diagnosis for the local MVP. Revisit the decision if someone must respond to a fault while nobody is watching. For a single active run, a supervised checker could reuse the existing coverage calculation, but would need lifecycle management, durable incident state, deduplication and a way to detect its own failure. For ongoing or multi-run monitoring, ADR-0034 already demonstrates Prometheus alert transitions. Reusing it would recover time-series history and rule evaluation at the cost of collector memory, integration, retention and notification routing. A separate decision should compare those costs against the required detection interval and name the responder. [On-demand health and resource costs](adr/0056-run-health-without-a-monitoring-stack.md) · [Prometheus evidence](adr/0034-local-observability-stack.md)

Run the incident drill separately on the registered F09 baseline. Declare the detection interval, pause serving while input and archive advance, and check whether the operator can identify the stalled stage. Resume serving and reconcile SQL with the known reference. If unattended alerting is later selected, repeat that drill with one delivered incident notification and one recovery, including their observed delays. The drill can use the existing replay path at any point independently of the unfamiliar-file work. [F09 recovery baseline](adr/0053-recording-recovery-boundaries.md)
